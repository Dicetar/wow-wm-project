# 03 - Report which requested capabilities can actually run

## Parent

[WM Autonomous Director V1](https://github.com/Dicetar/wow-wm-project/issues/5)

## What to build

WM and the operator see an evidence-backed capability answer: usable now, awaiting deployment, unsupported, or temporarily unavailable.

## Acceptance criteria

- [ ] Derive capability entries from the existing action registry/contracts, release schema catalog, shell behavior definitions, and deployment/proof records; do not introduce a competing action registry.
- [ ] Distinguish declaration, implementation, proof, enabled policy, and current deployment instead of equating a schema or native enum with usable capability.
- [ ] Classify a known action, a missing behavior, an installed shell, an uninstalled shell revision, and an infrastructure outage correctly through the public session capability view.
- [ ] Validate composite requirements as a unit and identify the exact missing primitive or unsupported combination without silently dropping it.
- [ ] Include capability/version/evidence references in planner input and proposed work so apply can reject stale assumptions.
- [ ] Missing mechanics are distinct from transient outages and from maintenance; only true capability gaps become development-request candidates.
- [ ] Test the classification using real registry/publisher adapters with substituted deployment facts, including denial of unsupported combinations.

## Blocked by

None - can start immediately.

## Verification and scope

Repo/API capability classification. Runtime proof is required before promoting a newly implemented capability, not to inventory a known unsupported one.

Use the existing WM workflow and relevant native/content skills. Preserve the Python/native ownership split, typed gates, current marker targeting, and unrelated working-tree changes. This is a complete user-visible or publicly verifiable slice; tests should exercise outcomes rather than source layout.
