# 11 - Finish generated-spell deployment and grant readiness

## Parent

[WM Autonomous Director V1](https://github.com/Dicetar/wow-wm-project/issues/5)

## What to build

A newly generated spell progresses from validated composition to matching server/client deployment and a usable grant, with maintenance and failure states clearly visible.

## Acceptance criteria

- [ ] Drive the existing unified DBC/shell audit/client patch pipeline from the generated composition without parallel materialization logic.
- [ ] Track the exact shell identity, behavior revision, server payload, client payload, and installed/runtime evidence in a durable deployment receipt.
- [ ] Distinguish usable existing deployed compositions from new identity/metadata requiring maintenance; do not unconditionally park every supported ability forever.
- [ ] Keep new patch/restart work staged for the established operator maintenance path; no silent realm restart or client-file replacement while in use.
- [ ] Grant only after required behavior and matching deployed server/client revision are available; a non-BROKEN audit or staged file alone is insufficient.
- [ ] Recover interrupted build/install/restart/grant steps using existing backups, conditional rollback, and receipts; never issue duplicate grants on resume.
- [ ] Verify actual spellbook/action state, icon, targeting/range, tooltip, duration, resource/cooldown, effect, and aura isolation for the generated identity.
- [ ] Exercise pending maintenance, failed/mismatched install, resumed deployment, successful cast, and revoke/rollback through panel and in-client proof.

## Blocked by

- [Compose functioning spells from reusable tested mechanics](https://github.com/Dicetar/wow-wm-project/issues/15)

## Verification and scope

Repo/native/publisher tests, installed payload verification, browser state, and in-client generated-spell proof.

Use the existing WM workflow and relevant native/content skills. Preserve the Python/native ownership split, typed gates, current marker targeting, and unrelated working-tree changes. This is a complete user-visible or publicly verifiable slice; tests should exercise outcomes rather than source layout.
