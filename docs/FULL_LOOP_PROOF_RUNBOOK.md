# Full-Loop Proof Runbook

This is the single ordered runbook for the two highest-priority live proofs:

- **P0-A**: native reactive bounty full loop —
  `trigger -> grant -> complete -> reward -> suppress -> cooldown -> regrant`.
- **ADR-0004 gate**: an arc quest generated by the factory/compiler (not a hand-clone)
  ships a correct reward panel in-client on a fresh reserved ID.

Both have been `PARTIAL` for many sessions because they were never run in one clean
window. Run this top-to-bottom in one window. Each phase has an explicit PASS gate and a
STOP rule. Do not tweak and retry blindly: after 3 failed fresh-ID attempts on the same
phase, stop and write the structural root cause (existing three-failure rule).

Player is `5406` / Jecia. BridgeLab MySQL is `127.0.0.1:33307`. Substitute as needed.

## 0. Clean-window preconditions

All must be true before starting. If any fails, fix it first — a dirty lab invalidates
every result below. Run `wm doctor --summary` first: it automates the mysql/world-db/
char-db/WM-bootstrap-table/native-bridge-scope/control-registry checks below and exits
non-zero if any FAIL. Treat its `FAIL` lines as hard blockers.

```powershell
git status --short --branch
$env:PYTHONPATH='src'
$env:WM_WORLD_DB_HOST='127.0.0.1'; $env:WM_WORLD_DB_PORT='33307'
$env:WM_CHAR_DB_HOST='127.0.0.1';  $env:WM_CHAR_DB_PORT='33307'
python -m pytest -q

```

## Part A — Native bounty full loop (P0-A)

### A1. Install one explicit bounty on a fresh reserved slot

```powershell
python -m wm.reactive.install_bounty --list-templates --summary
python -m wm.reactive.install_bounty --template-key <key> --player-guid 5406 --mode apply --summary
```

**PASS:** command reports a fresh reserved quest slot staged, rule installed for `5406`.
Record the quest id and rule key.
**STOP if:** the slot is not fresh, or the rule key collides with a stale rule — clean and restart Part A.

### A2. Trigger the grant

In-client: kill the bounty subject the required number of times within the window.

```powershell
python -m wm.control.audit --player-guid 5406 --summary
```

**PASS:** audit shows `quest_grant` proposal -> native `quest_add` request `done` ->
`quest/granted` bridge event -> `quest_granted` WM event. SOAP `.quest status <id> Jecia`
is `Incomplete`.
**STOP if:** no native request, or request not `done`. Capture the request id/status; do
not re-trigger more than 3 times.

### A3. Complete

In-client: finish the kill objective.

**PASS:** SOAP `.quest status <id> Jecia` is `Complete`; `character_queststatus`
shows the objective satisfied after `.saveall`.

### A4. Reward (turn in)

In-client: turn the quest in to the turn-in NPC.

**PASS:** reward panel shows the intended reward; reward item/money/XP delivered;
`quest/rewarded` bridge event recorded; WM post-reward cooldown row written for `5406`.
**STOP if:** reward panel is wrong/empty — this is the same class of failure ADR-0004
addresses. Record exact missing/wrong fields. Do not mutate the same visible quest id.

### A5. Suppress while cooling down

In-client: re-kill the subject during the post-reward cooldown.

**PASS:** no regrant occurs; audit shows suppression/cooldown, not a new grant.

### A6. Regrant after cooldown

Wait out `post-reward-cooldown-seconds`, then re-kill to threshold.

**PASS:** a fresh native `quest_add` request is submitted (trigger-scoped idempotency
key differs from A2), quest regranted, audit clean.

**Part A result:** label the loop `WORKING` only if A2–A6 all PASS in this one window.
Otherwise `PARTIAL` with the first failing phase and its evidence.

## Part B — Arc compiler-output proof (ADR-0004 gate)

Only start Part B if Part A passed (a clean reactive loop is a precondition).

### B1. Dry-run the factory scenario

```powershell
python -m wm.arcs.factory --scenario-json control\examples\arcs\<scenario>.json --mode dry-run --player-guid 5406 --summary
```

**PASS:** dry-run ok, fresh reserved quest slot selected, no freeform mutation fields,
journey plan validates. **Do not** substitute a hand-cloned quest row anywhere in B.

### B2. Apply (compiler output is the artifact)

```powershell
python -m wm.arcs.factory --scenario-json control\examples\arcs\<scenario>.json --mode apply --player-guid 5406 --runtime-sync auto --summary
```

**PASS:** quest published to the fresh id from compiler-generated SQL; runtime reload
sent; `wm_publish_log` + `wm_reserved_slot` (`active`, arc-tagged, scoped) rows present.

### B3. In-client accept + turn in

In-client: accept the arc quest from the intended starter NPC, complete it, turn it in.

**PASS:** quest log text correct; **reward panel correct**; reward item delivered;
arc/reward-instance rows recorded via the journey spine.
**STOP if:** reward panel wrong → per ADR-0004, the failing column set is the spec.
Add it to the compiler harvested-defaults/default map, burn ≤3 fresh ids per cycle,
rerun B. Never hand-clone to "make the proof pass."

### B4. Verify + lock the result

```powershell
python -m wm.arcs.factory --scenario-json control\examples\arcs\<scenario>.json --mode verify --player-guid 5406 --summary
```

**PASS:** verify returns `WORKING`; reward visibility confirmed by screenshot.

**Part B result:** on full PASS, relabel Arc + Reward Factory V1 gameplay `WORKING`,
move ADR-0004 to `ACCEPTED`, and update `docs/ROADMAP.md`,
`docs/WM_PLATFORM_HANDOFF.md`, and `docs/ARC_REWARD_FACTORY_V1.md` to cite the compiler
path (not hand-clone). Add the B3 regression test from ADR-0004 action item 4.
